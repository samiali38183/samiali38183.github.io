A small vulnerability intake service. Scanner findings go in; a remediation queue comes out, ranked by CISA KEV membership, EPSS, CVSS and asset criticality. The repository also shows what shipping it carefully looks like: authentication, rate limits, container hardening, Kubernetes and Terraform, and a CI pipeline that tests the controls. Coverage numbers do not show whether a test would notice a defect being introduced. After the first release (v0.1.0), each control got the same question: what would fail if it broke? Six places had no answer, and five more gaps turned up in how the controls were observed or built.

The problem

A raw scanner export sorts by CVSS, which puts a theoretical 9.8 ahead of a 7.5 that attackers are using today. KEV membership is the strongest prioritization signal that is freely available, so the service makes it the dominant factor and uses the rest to order everything else.

The second question is whether a small service like this can be shipped the way a production team would, with the security controls tested rather than described.

What it does

The score is 100 * (0.40*kev + 0.25*acr/8 + 0.20*epss + 0.20*cvss/10) / 1.05, from 0 to 100. The KEV weight equals the EPSS and CVSS weights combined, so a KEV finding never scores below a non-KEV finding on an asset with the same criticality; the one degenerate tie is broken in favor of KEV.

KEV is CISA's Known Exploited Vulnerabilities catalog: CVEs with evidence of exploitation in the wild. EPSS is a probability, from 0 to 1, that a CVE will be exploited in the next 30 days.

The API takes JSON findings or a Nessus/Tenable CSV export, upserts on (CVE, asset), and serves a ranked /queue, per-CVE views and stats. Scopes are findings:write, queue:read and admin. There are health, readiness and Prometheus endpoints, and a separate CLI command refreshes the KEV file from CISA so the API process never makes outbound calls.

Three implementation points

Key checks that do not leak timing

Keys are 256-bit random values and the server stores only their SHA-256. KeyStore.authenticate hashes the presented token and compares it against every stored digest with hmac.compare_digest, never exiting early, so response time does not reveal whether a key matched or how many bytes were right. A fast hash is deliberate: slow password hashes exist to protect low-entropy passwords, and running one on every request would hand an attacker a CPU lever. Until 0.1.1 no test would have noticed if that loop were changed; the two tests that now do are in the matrix.

Limiters in the right order

A token bucket per API key returns 429 with Retry-After. A second limiter counts failed authentications per source address and is checked before any key is looked at, so a brute-force attempt is throttled instead of getting free guesses. The failure limiter uses peek and charge so that checking does not itself spend a token. Both are in memory, which is a stated limitation: they are per replica and reset on restart. Clients behind one NAT or proxy share a budget, so an attacker there can lock legitimate clients out until the bucket refills.

Controls proven by tests, and a hash-locked build

The kind job does not just render the Helm chart. deploy/scripts/netpol-test.sh starts a labeled pod that must reach the service, an unlabeled pod in the same namespace that must time out, checks that the kevgate pod cannot open an outbound HTTPS connection, and submits a privileged pod that Pod Security restricted must reject. A second script then confirms that three of the four audit events the repository's Sigma rules target are in the API server audit log. Dependencies are pinned in requirements.lock with hashes; CI and the Docker build install it with --require-hashes and pip-audit scans that exact file. A weekly lock-freshness workflow is meant to fail when a fresh compile would change the lock; it had no run on record when this page was checked.

  • Nothing is deployed to a real AWS account. The Terraform (ECR, reports bucket, KMS key, workload and CI roles) was applied only to LocalStack, which has no ECR in its Community edition, so the ECR repository and the GitHub OIDC role are checked statically and by the terraform test. Nothing uses those resources: the service has no AWS SDK code and releases go to GHCR.
  • It runs one replica with SQLite on one volume and Recreate rollouts. That is a demonstration scope, and DEPLOYMENT.md lists what production would change (Postgres, replicas, tested backup and restore, key lifecycle). The rate limiter and the failure limiter are per process, per source address, and reset on restart.
  • The /metrics endpoint is unauthenticated. It carries counts, not findings, and is protected only by the NetworkPolicy.
  • There is no branch protection on main. The OIDC trust policy is pinned to refs/heads/main, so whoever can push to main controls what may assume that role. The role has no consumer today. The GitHub API returned "Branch not protected" for the repository on 2026-11-11.
  • The detection rules have not been run against a real SIEM or a live Prometheus. The Sigma rules convert with sigma and are validated, and three of four are checked by a jq translation against a real kind audit log. The alert rules are checked with promtool unit tests only.
  • Image signatures are not enforced. The release is signed and verified by its own job, but nothing at admission checks the signature, and there is no admission policy engine beyond Pod Security Admission.
  • The matrix maps claims to evidence, and it does not show sufficiency. A cited test passing shows that the behavior it asserts held on the tag, not that the control covers the threat. The repository's threat model lists the residual risks, and the matrix quotes them.
  • The scoring weights are a design choice and were not evaluated against remediation outcomes. Access control is coarse: three scopes, no per-asset authorization, no key expiry or rotation workflow, and revocation needs a restart.
  • The bundled KEV file is a 5-entry sample. kevgate kev-refresh downloads the real catalog, but the demo above used the sample.
