A static analyzer for Python web apps. It follows attacker-controlled input across functions and files and reports it only when it reaches a dangerous sink without a sanitizer for that bug class. {{bench:sinkline}} {{bench:sinkline-cap}}

The first reading is on code the engine was not built around. OWASP's BenchmarkPython v0.1 (commit f129148) is 1,230 small Flask test cases, each labeled vulnerable or safe in a published file. Ten of its 14 categories are source-to-sink flows, which is what sinkline is for: 240 vulnerable cases and 437 safe ones.

sinkline 0.4.1 reported 99 of the 240 vulnerable cases (TPR 0.41) and flagged 89 of the 437 safe ones (FPR 0.20), a score of +0.21 (TPR minus FPR). Two categories were close to blank: LDAP injection, 0 of 16, and XPath injection, 5 of 51. Command injection scored below zero (-0.26): it flagged 4 of 7 safe cases and only 4 of 13 vulnerable ones. Bandit 1.9.4 scored +0.07 and Semgrep OSS 1.185.0 +0.04 on the same ten categories, mostly because neither has rules for most of them.

TPR minus FPR is the benchmark's score. TPR is the share of vulnerable cases reported; FPR is the share of safe cases reported anyway. 0 means no better than guessing, 1 is perfect.

Over all 14 categories the order flips. Bandit scores +0.36 against sinkline 0.4.1's +0.10, because Bandit checks weak hashes (71 of 71) and weak random numbers (77 of 99), and sinkline has nothing for weak hashes, weak random numbers, cookie flags or what is stored in the session. It scores 0 on those four categories. Bandit still leads over all 14 with 0.5.0.

{{key:all14}} {{strips:all14}}

Separately, a flaw was found in sinkline's own GitHub Action. Its inputs (path, fail-on, min-confidence) were interpolated straight into a shell line with ${{ inputs.* }}, so a workflow that passed an attacker-influenced value could run arbitrary commands on the runner. Version 0.4.1 passes them through env:, quoted, and tests/test_action.py runs the script with hostile values.

Script injection (CWE-78) happens when untrusted text is pasted into a shell command, so the shell runs it as code. Passing it as an environment variable keeps it as data.

One more analysis bug is in the changelog: a try/except lost taint, so host = request.args["h"] followed by except: host = "localhost" reported nothing (fixed in 0.4.1; the command-injection example on Figure 1 has that shape).

The problem

A pattern linter reports every cursor.execute whether the argument came from a config file or from request.args, so reviewers learn to ignore it. The useful question is whether attacker-controlled data can reach the sink without passing through something that neutralizes it for this bug class.

In web apps that answer usually crosses a function or file boundary: a view reads request.form and a helper two files away builds the SQL.

What it does

Pure Python on the standard ast module, with no dependencies. It knows Flask, FastAPI, Django and aiohttp sources, and has 43 rules with 151 sink signatures mapped to OWASP 2021 and CWE. Output is text, JSON, SARIF 2.1.0 (with code flows) or a self-contained HTML report. It also ships as a GitHub Action and a pre-commit hook, and supports --baseline so an existing codebase can fail only on new findings.

{{diagram:sinkline}}

Three implementation points

Two-pass interprocedural summaries

Pass 1 analyzes each function with its parameters bound to symbolic labels (param:0, param:1, ...) and records which parameters reach the return value, which reach sinks, and whether the function is a thin sanitizer. It repeats until no summary changes, so a sink four helpers deep is found whatever order the helpers are defined in. Pass 2 re-runs with real sources and consults the summary at each call site. The cost is that summaries are context-insensitive: one per function, not per call site. Summary keys are module-qualified, so vulpy's bad/ and good/ trees, which define the same function names, give different results.

CWE-scoped sanitizers

A tainted value carries the set of CWEs it has been cleaned for. shlex.quote clears command injection only, html.escape clears XSS only, and int() clears everything. A single global "sanitized" flag makes a shell-safe string look SQL-safe. At a branch join, taint labels are unioned and cleared CWEs are intersected, so a value stays clean only if every path cleaned it. Validation guards such as if not x.isdigit(): abort() work the same way and are scoped too: a .. check is a path guard, not a shell guard. Figure 1 shows this with recorded output: the sanitizer step appears in the path, with the CWE it clears.

CWE numbers name bug classes: CWE-78 is OS command injection, CWE-79 cross-site scripting, CWE-89 SQL injection.

try/except needs a real join

Version 0.4.1 fixed a false negative where host = request.args["h"] followed by except: host = "localhost" lost the taint, because the handler body was visited in sequence after the try body. Taint after a try is now the join of the body (plus else) and each handler that does not exit, with handlers entered from the join of every state the body passed through.

  • The 0.5.1 score is not held out. The fixes (made in 0.5.0, unchanged on this suite in 0.5.1) were chosen by reading the failures of 0.4.1 on the same benchmark. Only the 0.4.1 reading is an independent measurement, and it was +0.21 on the taint categories.
  • One synthetic suite. BenchmarkPython v0.1 is a preliminary release of templated cases (many share one shape), and the SQL, command and XXE categories have only 5 to 13 vulnerable cases. The scorer is the repository's own script, not the official one, so the benchmark's own scorecard may differ.
  • High false-positive rate. FPR is 0.21 on the taint categories. The largest remaining source is position-sensitive lists (a list is tracked as a whole), then deliberately obfuscated safe variants. Taint stored through ConfigParser or a user-defined request wrapper is lost.
  • Four categories have no checks: weak hash, weak PRNG, cookie flags and trust boundary. Over all 14 categories Bandit leads, +0.36 to +0.27.
  • The self-labeled corpus is not independent. 109 lines, labeled alongside the engine, kept as a regression gate. Its F1 of 0.992 is not an accuracy estimate.
  • The public-project scans are unlabeled. Three of the four are deliberately vulnerable training apps. The one microblog finding is parameter injection into a fixed host, which sinkline labels SSRF, not a proven SSRF, and its redirect check is still treated as a guard. Neither the new findings nor the absence of others is a measure of accuracy. No CVEs or real-world vulnerabilities are claimed.
  • Figure 1 shows recorded runs of small files, not a benchmark. One case is worth knowing: return shlex.quote(request.args.get("name", "")), is not reported in 0.5.1 (the changelog says a returned call result counts as XSS only when it is the tainted string itself, and an unknown call is not guessed at), while the same value assigned to a variable first is. The recorded run is in assets/data/sinkline-bench/html-wrong-direct.txt. Changes made on main after the v0.5.1 tag now report the direct return as XSS (CWE-79), so a newer sinkline would not match that recording.
  • Known design limits. Taint passed between requests through a module global, returned closures, dynamic dispatch, and instance fields tracked per class rather than per object. Python only, summaries context-insensitive, and no coverage for OWASP A04 and A06.
