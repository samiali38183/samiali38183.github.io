A localhost-only training lab: three small Flask services, each with one textbook web bug (SSRF through a redirect, SQL injection in ORDER BY, a missing object-level authorization check). Every lab has a fixed version, tests that show the impact on the vulnerable service and then the same checks failing against the fix, a Sigma rule replayed on recorded logs, and a record of what sinkline does and does not report. It is a training lab, not vulnerability research. {{bench:vulnlab}} {{bench:vulnlab-cap}}

Each vulnerable service is under 60 lines, has no comment pointing at its bug, and does the intended job. What goes wrong is one missing check, and each test first confirms that the intended protection works for the direct case, then shows the impact. Everything the tests touch is data the test created: a marker string, a temporary SQLite file, seeded records.

CWE-639		An invoice API checks that the caller is logged in on the read-by-id route but not that the invoice is theirs. The list and update routes do check.Each route re-implements the rule by hand and one forgot.

A logged-in user's own list contained only their invoices. Asking for another user's invoice returned 200 with that user's memo, and all eight ids answered 200. On the same record the update route already answered 404, so the inconsistency is part of the evidence.
IDOR and BOLA name the same flaw: the server trusts an object id from the client without checking that the caller may use that object (OWASP API1:2023, CWE-639). Sequential ids make other records easy to find but are not the bug; random ids would only make a missing check harder to exploit.

Each fix is small and each lab's tests show it from two sides: the impact check that passed on the vulnerable service fails on the fix, and a second test shows the fixed service still does its job, so a fix that breaks the feature is not accepted. The three labs' own tests (72) and the tests of the loopback guard, the harness, the replay code, the captured output and the Sigma rules (65) all pass: 137 in all.

The write-ups say why. sinkline reports a tainted value reaching a dangerous call; it does not recognize a custom allow-list or address check as a sanitizer, and treats a dictionary lookup against constant column names as a pass-through, so it cannot tell the fixes from the bugs in labs 01 and 02. On lab 01 it also does not say that the bug is the redirect: "tainted URL reaches requests.get" would be just as true of an app with no allow-list at all. Lab 03 has no tainted value reaching a sink: the id is used only as a dictionary key, and whether the caller may see the record is a rule of the application that a source-to-sink analyzer has no model of. Finding that class takes authorization tests, a policy layer that fails closed, or review against an access matrix.

The lab was not changed to hide any of this.

Shape of a lab

Each lab is a directory with a vulnerable/app.py and a fixed/app.py (a Flask app with a create_app(settings) function), a lab.py that starts the services for one variant on free loopback ports, test_lab.py, a write-up, the captured sinkline output and a detection/ directory with a Sigma rule and two recorded access logs. The two app files differ only where the fix is.

Four statements per lab, each a test

  1. Proof on the vulnerable service: a control first (the intended protection works for the direct case), then the observable impact.
  2. The same request against the fixed service does not produce the impact.
  3. The fixed service still does its job.
  4. The detection rule fires on the recorded attack log and not on the recorded benign log, and the attempt against the fixed service is still visible to the rule.

Access log and detection

The harness appends one JSON object per request to a log file: timestamp, client address, method, path, raw query string, status, a short hash of the Authorization header as session and the route's object_id. Field names follow W3C-style web-server logs, so the rules read like web-server rules. Single-event rules are compiled by tripline's engine (pySigma parses, tripline walks the condition tree), with its logsource router bypassed because that router knows only Windows, Linux auditd and CloudTrail. Lab 03's rule is a correlation (an event count of distinct object_id values per session within a minute) that tripline does not implement, so the lab's own windowing code in vulnlab_common/replay.py evaluates it.

Safety scope

Everything binds to loopback. The harness refuses to start a service on any other host, and every request the tests make goes through a client that checks the URL first and accepts only localhost or a literal loopback address, with no DNS lookup. The stand-in "internal" address in lab 01 is 127.0.0.2, which is still loopback. 26 tests under tests/ assert the guard, including look-alike names and private and link-local addresses, and that no lab test names a non-loopback URL. There is no shell, persistence, evasion or scanning code in the repository.

  • It is a training lab, and the bugs are simpler than real ones. Each is a textbook class written small enough to fit on one screen: one file, one bug, in-memory or temporary data, no framework configuration, no concurrency and no real identity provider. Finding such a bug in real code is the hard part, and these labs do not exercise it.
  • There are no CVEs, no disclosures and no findings against real software. None are claimed, and no real product or vendor is reproduced.
  • Scope is loopback only. The services run on 127.0.0.1 and start on random ports, and the repository's own guard refuses anything else. It is not a scanner, an exploitation toolkit or a target for anything else, and the vulnerable apps must not be deployed or exposed on a network.
  • sinkline reports both fixed injection-style services, because it does not recognize a custom allow-list, address check or constant-column lookup as a sanitizer. Those two findings are false positives. It reports nothing on the missing-authorization lab, vulnerable or fixed, because that bug is not a taint flow. That is the blind spot of static taint analysis, not a defect of the scan.
  • The detection rules see attempts, not impact. They fire on the fixed services too. Lab 01's rule matches literal internal and metadata addresses and misses an internal target named by hostname or written in another address form. Lab 02's matches anything in the sort value other than letters, digits and underscore, so a client that legitimately sends a multi-column sort would be a false positive.
  • The IDOR rule is a correlation with an untuned threshold. Five or more distinct invoice ids per session in a minute is evaluated by the lab's own windowing code, since tripline has no correlation support. A single targeted read of one other user's invoice produces no alert at all. That is the real gap: this class has no request-level signature.
  • The fixes are checked by the tests listed, not proven. Lab 01's fix accepts only http, because pinning an address for https needs a custom adapter that keeps SNI and certificate checks on the original hostname, and that is not done here. Nothing was tested against real traffic.
  • The page shows recorded results. It evaluates nothing, runs no service and sends no request. Request strings and logs are not reproduced here. The observable results are described in prose and the labs' own tests are linked below.

The sinkline text files recorded in the repository (labs/*/sinkline/*.txt) showed the path glyphs as garbled characters in v0.1.0, a character-encoding slip when they were written on Windows; v0.1.1 stores them as UTF-8 and a test guards that.
