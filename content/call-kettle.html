Call Kettle

Call Kettle answers inbound calls for small home-service businesses. Twilio delivers the call, a Claude model holds the conversation, and a FastAPI backend books, moves and cancels appointments in SQLite. Because anyone can phone it, the model's output is treated as untrusted input.

The design splits the system into a model that proposes tool calls and server code that authorizes them. Every call passes authorize_tool_call: tenant binding, known tool, tenant policy, after-hours rule, argument schema and per-call budgets, with default deny. Behind it, the tools enforce ownership, a service allow-list, the slot grid and a SQLite overlap check. Identity comes from the call rather than the model's arguments, so a transfer goes to the tenant's configured number and a confirmation text goes only to the caller ID.

The offline evaluation uses a scripted model that does whatever an attacker wants, while the real agent loop, gate, tools and a fresh database handle it. Its 48 cases (42 attacks, 6 normal-use controls) cover prompt injection, including text planted in tool results, cross-tenant access, argument tampering, claim forgery, data leakage, loop exhaustion and retries. All pass. Nineteen more tests each remove one safety check and must see cases fail.

Limits

  • The scripted model shows what the server does when the model misbehaves, not how often a real model would. No live-model evaluation exists.
  • The gate and the evaluation exist in the public repository, which is a sanitized snapshot. They are not in the deployed private code.
  • Spoofed caller ID, unverified booking phone numbers and DNS rebinding on webhook URLs are documented limitations and are not tested.
  • Reviewing the boundary found six defects, including a confirmation text that went to a caller-supplied number. Each was fixed and has a case.
