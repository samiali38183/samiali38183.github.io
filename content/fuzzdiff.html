fuzzdiff

picohttpparser, an HTTP/1.x parser written in C, ported to safe Rust and checked against the C original by running both on the same input and reporting any difference.

The problem

Network parsers written in C keep having the same bugs: reads past the end of a buffer, length arithmetic that wraps, off-by-ones, half-initialized output. Rewriting one in a memory-safe language is a fair answer only if the rewrite behaves like the original.

picohttpparser is a good test subject: 715 lines of C, MIT or Perl licensed, hostile-input facing, and full of the pointer idioms that cause those bugs. The project asks whether a port can be shown to behave identically, instead of just saying so.

What it does

The Rust crate has #![forbid(unsafe_code)], no dependencies and no allocation, and covers request heads, response heads, header blocks and an incremental in-place chunked decoder. The vendored C (commit dd573d8, unmodified, hashes checked) is built next to it. A harness decodes fuzzer bytes into a case (which entry point, header capacity, last_len, how a chunked body is split across calls), runs both, and classifies the result as Equal, BothReject, RustStricter (one of two documented deviations) or Divergence. A divergence fails the tests and the CI fuzz job.

Four implementation points

A chunked decoder with no pointer arithmetic

The C decoder walks the buffer with pointers. The Rust one (src/chunked.rs) is an eight-state machine (Size, Ext, HeaderLf, Data, DataCr, DataLf, TrailerHead, TrailerMiddle) over two indices into the slice. Every read is buf.get(src), so running out of input is a break out of the loop, not an out-of-bounds read, and body bytes are moved to the front with copy_within(src..src + take, dst) where take is capped by what has arrived and what the chunk still needs. The hex-digit cap (usize::BITS / 4) and the framing-overhead ratio check after 102,400 bytes are kept, because the digit cap is what stops a long size line from wrapping, the class behind CVE-2013-2028 in nginx.

The request line has to fail in C's order

C reports "need more data" (-2) or "error" (-1) depending on which check it reaches first, so a port that validates in a different order disagrees on truncated input. request() follows the C sequence: skip a stray leading CRLF, read the method token, skip spaces, read the target, skip spaces, only then reject an empty method or path, then the version. Missing data anywhere propagates as Partial through ?. The corpus replay tests every prefix length of every input with an incremental last_len to hold this down.

The seeded bugs vanish when the feature is off

To show the harness can see bugs, src/mutants.rs adds three deliberate ones behind a mutants feature: a header value one byte short, a missing end-of-buffer guard, and the wrong chunked state after a trailer line. Without the feature the check is const fn active(..) -> bool { false }, so the shipped parser contains none of it. With the feature on, the state lives in a thread-local, so tests can switch bugs on one at a time.

Exact-size copies so the sanitizer can see over-reads

A C over-read that lands inside a larger allocation goes unnoticed. The C shim (c/shim.c) copies each input into a heap block of exactly len bytes (dup_exact), so one byte past the end is outside the allocation and AddressSanitizer reports it. The shim also returns offsets instead of pointers so the harness can compare results by value.

Limitations

  • The fuzz runs are short. Two minutes per target is a smoke run, not assurance. Miri has not been run.
  • The SIMD C path is not reached by libFuzzer. The diff and c_only targets build the C side without -msse4.2. That path was exercised only by the sanitizer test job, with the corpus and property tests.
  • No new vulnerability was found. picohttpparser has no published security advisory, and the advisories discussed in CVE_CLASSES.md are examples of bug classes, mostly from other parsers.
  • The Rust port is slower on head parsing, and the cause was not profiled. On Windows the C side ran its portable path, so a Linux build with SIMD may widen the gap; that was not measured.
  • Two deliberate deviations. D1: optional rejection of folded header lines, off by default. D2: last_len larger than the buffer is an error in Rust, while C reads out of bounds. D2 was found by reading the code, has not been reproduced under a sanitizer, and the fuzz targets clamp last_len, so no fuzz run reaches it. Details in DEVIATIONS.md.
  • Blind generator. The 27.6 million-input seeded generator run in the README has no coverage feedback and is a stand-in for fuzzing, not a replacement.
