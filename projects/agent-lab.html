Agent Engineering Lab — multi-agent builds, voice stacks, and security

How I build with Hermes Agent, Claude Code and Codex: parallel sub-agents, pytest as the gate, benchmarks before opinions, and security reviewed like a production system.

Agent Orchestration Voice AI AppSec
Public write-up: github.com/samiali38183/agent-engineering-lab. Real engineering notes from a live project; customer data, prices and secrets are not in it.

The stack

  • Runtime: FastAPI on Fly.io with a persistent volume and SQLite in WAL mode as the system of record (calls, bookings, tenants, usage).
  • Telephony and speech: Twilio today; Deepgram streaming speech-to-text and Amazon Polly voices; ElevenLabs, Telnyx and Retell in a controlled benchmark.
  • Reasoning: Claude tool-use loop with schema-validated tools. The model proposes; code disposes.
  • Integrations: Google Calendar, Cal.com, Calendly and iCal busy feeds behind one provider interface.
  • Agent tooling: Hermes Agent as orchestrator, Claude Code and Codex as builders, parallel sub-agents on isolated workstreams.

How I use agents

  1. Split work into streams. One orchestration session fans out independent sub-agents (voice audit, coverage routing, usage metering, calendar audit, portal UI, concurrency, field-service research) with disjoint files and explicit "do not touch" lists.
  2. The test suite is the contract. The backend suite is 3,400+ tests. After every fan-out I re-run the affected slice, diff against a clean baseline worktree, and accept only regressions I can explain.
  3. Claim levels, not vibes. Every feature is labeled BUILT, UNIT TESTED, INTEGRATION TESTED, DEPLOYED or PRODUCTION VERIFIED, and nothing is marketed above its level.
  4. Measured vs modeled. Cost and latency numbers are tagged so a model never passes as a measurement.
  5. No secrets in prompts. Keys live in gitignored env files or platform secrets and are checked with read-only calls.

Voice-stack benchmark harness

Instead of arguing about which voice stack is best, I built a reproducible harness: 28 scenarios (booking, reschedule, cancel, transfer, emergencies, barge-in, noisy audio, tool failure, a business timezone that differs from the server) driven through the real conversation engine. A deterministic stub model keeps CI free, and a live flag runs real models. Scoring covers booking correctness, tool-call correctness, hallucination checks, transfer correctness and recovery, with slots for latency percentiles and speech accuracy from real-call runs. Architectures under comparison: the Twilio baseline, Deepgram streaming, Telnyx managed and custom, Retell, ElevenLabs voices, and native audio models.

Databases and concurrency: a real race the analysis found

A per-client concurrent-call ceiling looked correct but was not atomic. Under a burst of 64 simultaneous callers it admitted 42 against a ceiling of 24, a classic check-then-insert race. The fix was an admission lock around the count-and-claim step, with a hard global cap and a rollback-safe default. A local load test now holds the ceiling exactly at 8, 16, 32 and 64 callers. SQLite WAL, a single Fly machine and a shared model client were analysed as the real scaling limits, and the write-up marks which claims are measured and which are modeled.

Security engineering inside an agent system

  • Webhook authenticity: telephony webhooks are signature-verified, with duplicate-event handling tested.
  • Tenant isolation: every portal query is scoped by the signed-in session, with tests that one tenant's calls never appear for another.
  • Output escaping and CSRF: portal pages escape all dynamic text, and write routes require CSRF tokens.
  • Claim and injection guards: the agent cannot confirm a booking unless the tool actually succeeded, and tool arguments are validated before execution.
  • Cost-abuse limits: worst-case spend per customer is modeled so a runaway caller cannot create an unbounded bill.
  • Data minimisation: caller emails are purged after appointments, and secrets are never committed.
  • Honest disclosure: the voice persona sounds natural but never claims to be human and answers truthfully if sincerely asked.

What this taught me

Agents are fast; verification is the bottleneck. The valuable skills were scoping sub-agents so they cannot collide, demanding evidence (tests, baselines, load runs) before trusting a summary, and treating a voice agent like any internet-facing service: authenticated inputs, bounded cost, isolated tenants and an audit trail. It is the same mindset I bring to vulnerability management and detection work.
