As foundTwo seeded bugs no test noticed, and a harness exception that would have hidden one

Version 0.1.0 compared the Rust port with one reference, the C original, and four things were weak. The harness exception for folded headers (D1) applied to any Rust ObsFold error in strict mode, so a bug that reported ObsFold on a normal header would have passed as expected (pull request #2 narrowed it: the input must contain a line feed followed by a space or tab, otherwise it is a divergence). A mutation sweep of the three seeded bugs then found two one-line changes to the parser that no test noticed. The libFuzzer runs were two minutes per target, with the C SIMD path never reached. And “matches picohttpparser” said nothing about any other parser.

Differential testing runs two implementations on the same input and flags any difference. It needs a rule for which differences are expected, and a second opinion to show what “same as the original” does and does not mean.

Three-way comparison with httparse

httparse 1.10.1 (pinned exactly) is the HTTP/1.x parser hyper builds on. It was added as a third parser so that “matches the C original” can be compared with “matches a production Rust parser”. The result is a map of leniency choices, not a list of bugs: each class is pinned by a test, and a new class fails CI. Numbers are from docs/DIFFERENTIAL_HTTPARSE.md; the table is copied from its generated block.

Sweep of 2,000,000 deterministic inputs (999,999 request, 500,001 response, 500,000 header block; half from the corpus, half from the well-formed generators, two thirds then mutated). All three parsers did the same thing on 1,390,722 (69.54%) and disagreed on 609,278. picohttpparser and fuzzdiff differed on 0; disagreements that no documented class explains: 0; 36,905 are only httparse rejecting an invalid prefix earlier than the other two. The share is large because the mutator produces folds, doubled spaces and version digits constantly, not because the parsers disagree on typical traffic.

In words, as the repository states them:

  • httparse is stricter on obsolete line folding (RFC 9112 section 5.2), more than one SP between request-line elements, HTTP/1.x with x other than 0 or 1, and octets 0x80 to 0xFF in the request-target.
  • picohttpparser, and so fuzzdiff by default, is stricter on more than one empty line before the request-line, a response status code outside 100 to 599, bare LF inside a chunk extension, and an empty chunk size.
  • Same verdict, different fields: extra SP before a reason phrase, and obs-text in a reason phrase.
  • Different cut-off on partial input: httparse rejects an already-invalid prefix before picohttpparser says it needs more bytes.
  • All three agree, for example, on rejecting whitespace before the colon, bare CR and NUL, and on accepting 0x80 in a field value.

Method

How it works

design, implementation points and diagram

The problem

Network parsers written in C keep having the same bugs: reads past the end of a buffer, length arithmetic that wraps, off-by-ones, half-initialized output. Rewriting one in a memory-safe language is a fair answer only if the rewrite behaves like the original.

picohttpparser is a good test subject: 715 lines of C, MIT or Perl licensed, hostile-input facing, and full of the pointer idioms that cause those bugs. The project asks whether a port can be shown to behave identically, instead of just saying so, and then what “identically” leaves out.

What it does

The Rust crate has #![forbid(unsafe_code)], no dependencies and no allocation, and covers request heads, response heads, header blocks and an incremental in-place chunked decoder. The vendored C (commit dd573d8, unmodified, hashes checked) is built next to it. A harness decodes fuzzer bytes into a case (which entry point, header capacity, last_len, how a chunked body is split across calls), runs both, and classifies the result as Equal, BothReject, RustStricter (one of two documented deviations) or Divergence. A divergence fails the tests and the CI fuzz job. Since 0.2.0 an oracle runs the same head through httparse as well and sorts every disagreement into a documented class.

Four implementation points

A chunked decoder with no pointer arithmetic

The C decoder walks the buffer with pointers. The Rust one (src/chunked.rs) is an eight-state machine (Size, Ext, HeaderLf, Data, DataCr, DataLf, TrailerHead, TrailerMiddle) over two indices into the slice. Every read is buf.get(src), so running out of input is a break out of the loop, not an out-of-bounds read, and body bytes are moved to the front with copy_within(src..src + take, dst) where take is capped by what has arrived and what the chunk still needs. The hex-digit cap (usize::BITS / 4) and the framing-overhead ratio check after 102,400 bytes are kept, because the digit cap is what stops a long size line from wrapping, the class behind CVE-2013-2028 in nginx.

The request line has to fail in C's order

C reports “need more data” (-2) or “error” (-1) depending on which check it reaches first, so a port that validates in a different order disagrees on truncated input. request() follows the C sequence: skip a stray leading CRLF, read the method token, skip spaces, read the target, skip spaces, only then reject an empty method or path, then the version. Missing data anywhere propagates as Partial through ?. The corpus replay tests every prefix length of every input with an incremental last_len to hold this down.

The seeded bugs vanish when the feature is off

To show the harness can see bugs, src/mutants.rs adds five deliberate ones behind a mutants feature: a header value one byte short, a missing end-of-buffer guard, the wrong chunked state after a trailer line, the chunk overhead guard at 80% instead of 75%, and a status-line guard that waits for 3 bytes instead of 4. Without the feature the check is const fn active(..) -> bool { false }, so the shipped parser contains none of it. With the feature on, the state lives in a thread-local, so tests can switch bugs on one at a time. The last two were added after a mutation sweep found them undetected.

Exact-size copies so the sanitizer can see over-reads

A C over-read that lands inside a larger allocation goes unnoticed. The C shim (c/shim.c) copies each input into a heap block of exactly len bytes (dup_exact), so one byte past the end is outside the allocation and AddressSanitizer reports it. The shim also returns offsets instead of pointers so the harness can compare results by value.

Tolerance and limitsWhat the numbers do not show

  • The fuzz runs are short. Two minutes per leg is a smoke run, not assurance, and the libFuzzer targets never reach the overhead guard or the last_len case (D2). No 32-bit or big-endian target has been run.
  • No new vulnerability was found. picohttpparser has no published security advisory, the httparse differences are leniency choices and not defects in the C code, and the advisories in CVE_CLASSES.md are examples of bug classes, mostly from other parsers.
  • Miri covers the pure-Rust crate only. The C code and the FFI harness cannot run under it, so the comparison with C is not covered by Miri. The crate forbids unsafe code, so there is little for it to find.
  • The httparse comparison is narrow. It covers head parsing and the first chunk-size line only (httparse has no chunked decoder), httparse in its default configuration, two parsers on one input and not a proxy and server pair, and 64 header slots on each side.
  • Five seeded bugs are a small sample. Three are caught in under 300 generated inputs, which shows the plumbing works; one is caught only by a hand-built case because the random generator never builds that input.
  • The Rust port is slower on head parsing (about 1.4x to 1.5x), and the cause was not profiled. On Windows the C side ran its portable path, so a Linux build with SIMD may widen the gap; that was not measured.
  • Two deliberate deviations. D1: optional rejection of folded header lines, off by default. D2: last_len larger than the buffer is an error in Rust, while C reads out of bounds. D2 was found by reading the code and has not been reproduced under a sanitizer. Details in DEVIATIONS.md.
  • Blind generator. The 27.6 million-input seeded generator run in the README has no coverage feedback and is a stand-in for fuzzing, not a replacement.
