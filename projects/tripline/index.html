tripline

A CI gate for detection rules. It replays recorded attack telemetry through Sigma rules on every pull request and fails the build when a rule that should fire does not. Version 0.3.0 adds a benign corpus, a sweep of evasion variants and a coverage figure split by who wrote the passing rules.

As leftA replacement rule matches the two chmod runs, and the gaps are now measured

The replacement rule anchors on the chmod binary (and, since the sweep below found the gap, on busybox chmod) and handles symbolic and octal forms. Its two matches on the recorded fixture are the two chmod executions. The upstream rule stays in the rule set, so a future upstream fix is picked up automatically.

Rules written in this repository carry part of the headline. Six rules were written for this project (the setuid replacement, three AWS rules and two Windows rules), and five of the 13 passing scenarios depend on them. Coverage is therefore shown as two figures, always together: 98% of weight points have a passing scenario (61 of 62), but only 52% (32 of 62, 8 scenarios) pass on unmodified SigmaHQ rules alone. tripline computes the split from each expected rule's author field.

Method

How it works

design, implementation points and diagram

The problem

Detection teams count rules and ATT&CK tags. Neither number says whether a rule still fires on the behavior it is named after, and a syntax linter passes rules that never matched anything.

tripline treats a rule like code under test: each scenario names a technique, the Sigma rules that must fire, and recorded telemetry to replay. If an expected rule misses, the exit code is 1. Separately, every rule is replayed over a benign corpus and over generated variants of the attack commands, and the counts are reported.

It is not the first tool to test detections against recorded or generated telemetry: SigmaHQ's regression data, rsigma backtest, SCYTHE's pipeline and Splunk's attack_data each do a version of this. tripline adds a small scenario layer (the technique, the expected rules and the fixture live together in one repository), a plain-Python evaluator that runs offline, and a weighted scorecard. It does not replace any of them (comparison).

What it does

14 scenarios cover 14 ATT&CK techniques across AWS, Linux and Windows. Linux and Windows telemetry comes from Atomic Red Team tests run on GitHub-hosted CI runners; the AWS plane replays public CloudTrail data (Stratus Red Team detonation logs and the flaws.cloud dataset). Rules are compiled to Python and evaluated offline against committed NDJSON, so the whole gate runs in seconds with no SIEM. Output is a JSON scorecard, JUnit XML, an ATT&CK Navigator layer (ATT&CK v20) and a static HTML report.

Coverage is weighted by how common each technique is, so breaking a common technique moves the headline more than breaking a rare one. Weights run from 1 to 10: 45 of the 62 points follow Red Canary's public 2026 top-10 ranking (weight = 11 minus rank, seven scenarios) and 17 are hand-assigned low values for the seven scenarios outside that top 10 (docs/weights.md).

Describe this diagram
  1. Emulate and record. Atomic Red Team on CI runners; public AWS logs.
  2. Fixtures committed to the repo. run.ndjson and manifest.json, reviewed by a person.
  3. Compile Sigma rules to predicates. pySigma parses; tripline walks the condition tree.
  4. Logsource router. a rule only sees events its logsource matches.
  5. Replay and score per scenario. weights from technique prevalence.
  6. Gate: exit 1 if an expected rule misses. scorecard, JUnit, ATT&CK Navigator layer, HTML.

Three implementation points

Compiling the Sigma condition tree into Python predicates

pySigma parses each rule and applies value modifiers. tripline then walks the resulting condition tree and turns every leaf into a closure over an event (tripline/engine/compiler.py): contains, startswith, endswith, all, re, windash, base64offset, cidr, fieldref, numeric comparisons, 1 of and all of. Anything it cannot evaluate raises UnsupportedRuleError, and a scenario whose expected rule failed to compile counts as failed. A gate that cannot evaluate a rule must not pass it. A code review of 0.2.1 found tripline breaking its own rule: timestamp part modifiers such as |hour compiled but never matched. They now evaluate or raise.

Telemetry sliced by run GUID

The Linux workflow wraps every Atomic test in two marker commands, tripline-marker RUN TEST start and ... end. They are ordinary execve events, so attribution lives inside the audit log itself. The collector merges auditd records by serial, hex-decodes EXECVE arguments and keeps only what falls between a pair of markers carrying the run's GUID. Before 0.2.1 a marker from another run in the same log could open or close a window, or leak events from an earlier run; markers with a foreign GUID are now ignored. For cloud data, tripline cloud build shifts eventTime while keeping offsets and appends tripline/<run-guid> to userAgent.

A routing problem is not a missed detection

A rule is evaluated only on events its logsource matches, and results read 1/7 applicable events. If a rule has no applicable events at all, that is reported as a routing problem (wrong product, category or service). 0/7 applicable events (rule did not match) is the real miss. They are separate values of outcome in scorecard.json, the CLI, JUnit and the HTML report, because the fix for each is different. The benign corpus follows the same rule: a rule with no applicable benign events is listed as not evaluated, never as zero false positives.

Sigma is an open, vendor-neutral format for detection rules. A rule's logsource says which kind of log it applies to.

Tolerance and limitsWhat the numbers do not show

  • Three emulation runs linked above show failed. The Linux run 41838714456 failed because the stock setuid rule missed (the finding itself). The two Windows recording runs failed their last step, which asserts that expected rules fire. In the later one, 43090565998, that step failed four scenarios (T1027, T1053.005, T1059.001, T1059.003) against the scenario definitions of that commit; the scenarios were then changed (two now expect rules written in this repository, one was narrowed) and the committed fixtures pass against the changed definitions. The workflows still upload the recorded telemetry, and a maintainer reviews it before committing it as a fixture. The passing gate is the ci run, which replays the committed fixtures.
  • 98% is not the whole story. Only 52% of weight points pass on unmodified SigmaHQ rules alone; the rest depend on rules written in this repository, two of them tuned to the Atomic tests' command shape. The pending scenario counts as zero in both figures.
  • A pass is a recall check on one recording. A scenario passes when each expected rule fires on at least one event. The benign corpus is one 33-second Linux recording, so a Windows or AWS rule that fired on everything would still pass.
  • The evasion sweep covers three Linux scenarios. Its variants are hand-written, evaluated as audit events and never executed, and a catch rate over them does not measure real-world evasion.
  • One Windows scenario is still pending. T1027 has no accepted recording: its expected rule matched 0 of 15 events in the latest recording, and re-labelling it to expect another rule would raise the number without testing an obfuscation rule (F-003).
  • Small coverage. 14 techniques out of several hundred. The 98% and the 52% are progress against this repo's own list, not a statement about any organization. 17 of the 62 weight points are hand-assigned, and the ranking behind the other 45 is Red Canary's customer detections, a proxy for prevalence in other environments.
  • The cloud plane is replayed, not detonated by this project. The records are real CloudTrail from public datasets, but the cloud rules written for the project sit beside fixtures from the same datasets, so those passes show the wiring works, not that the rules generalize.
  • A different evaluator from production. There is no parity test against a real SIEM backend, so a pass is necessary, not sufficient.
