SigmaHQ's Setuid and Setgid rule looks for the literal text chmod u+s. Atomic Red Team's T1548.001 tests run chmod u+xs, and chmod 4755, ug+s or a+s would slip past the same way. Replaying the recorded fixture through both rules (a small script against tripline's own API):

setuid and setgid are file mode bits that make a program run with the privileges of its owner or group. A root-owned program with the bit set is a classic way to keep root access (ATT&CK T1548.001).

MethodHow it works

The problem

Detection teams count rules and ATT&CK tags. Neither number says whether a rule still fires on the behavior it is named after, and a syntax linter passes rules that never matched anything.

tripline treats a rule like code under test: each scenario names a technique, the Sigma rules that must fire, and recorded telemetry to replay. If an expected rule misses, the exit code is 1.

What it does

14 scenarios cover 14 ATT&CK techniques across AWS, Linux and Windows. Linux and Windows telemetry comes from Atomic Red Team tests run on GitHub-hosted CI runners; the AWS plane replays public CloudTrail data (Stratus Red Team detonation logs and the flaws.cloud dataset). Rules are compiled to Python and evaluated offline against committed NDJSON, so the whole gate runs in seconds with no SIEM. Output is a JSON scorecard, JUnit XML, an ATT&CK Navigator layer and a static HTML report.

Coverage is weighted by how common each technique is (weights 1 to 10 from the Red Canary 2026 Threat Detection Report ranking, mapped by hand), so breaking a common technique moves the headline more than breaking a rare one.

Describe this diagram
  1. Emulate and record. Atomic Red Team on CI runners; public AWS logs.
  2. Fixtures committed to the repo. run.ndjson and manifest.json, reviewed by a person.
  3. Compile Sigma rules to predicates. pySigma parses; tripline walks the condition tree.
  4. Logsource router. a rule only sees events its logsource matches.
  5. Replay and score per scenario. weights from technique prevalence.
  6. Gate: exit 1 if an expected rule misses. scorecard, JUnit, ATT&CK Navigator layer, HTML.

Three implementation points

Compiling the Sigma condition tree into Python predicates

pySigma parses each rule and applies value modifiers. tripline then walks the resulting condition tree and turns every leaf into a closure over an event (tripline/engine/compiler.py): contains, startswith, endswith, all, re, windash, base64offset, cidr, fieldref, numeric comparisons, 1 of and all of. Anything it cannot evaluate raises UnsupportedRuleError, and a scenario whose expected rule failed to compile counts as failed. A gate that cannot evaluate a rule must not pass it. A code review of 0.2.1 found tripline breaking its own rule: timestamp part modifiers such as |hour compiled but never matched. They now evaluate or raise.

Telemetry sliced by run GUID

The Linux workflow wraps every Atomic test in two marker commands, tripline-marker RUN TEST start and ... end. They are ordinary execve events, so attribution lives inside the audit log itself. The collector merges auditd records by serial, hex-decodes EXECVE arguments and keeps only what falls between a pair of markers carrying the run's GUID. Before 0.2.1 a marker from another run in the same log could open or close a window, or leak events from an earlier run; markers with a foreign GUID are now ignored. For cloud data, tripline cloud build shifts eventTime while keeping offsets and appends tripline/<run-guid> to userAgent.

A routing problem is not a missed detection

A rule is evaluated only on events its logsource matches, and results read 1/7 applicable events. If a rule has no applicable events at all, that is reported as a routing problem (wrong product, category or service). 0/7 applicable events (rule did not match) is the real miss. They are separate values of outcome in scorecard.json, the CLI, JUnit and the HTML report, because the fix for each is different.

Sigma is an open, vendor-neutral format for detection rules. A rule's logsource says which kind of log it applies to.

Tolerance and limitsWhat the numbers do not show

  • The two emulation runs linked above are failed on GitHub. Their last step, which asserts that the expected rules fire, failed: in the Linux run because the stock setuid rule missed (the finding itself), in the Windows run because some scenarios did not pass. The workflows still upload the recorded telemetry, and a maintainer reviews it before committing it as a fixture. The passing gate is the ci run, which replays the committed fixtures.
  • A pass is a recall check on one recording. A scenario passes when each expected rule fires on at least one event. There is no benign corpus yet, so a rule that fires on everything would also pass, and there are no evasion variants.
  • Four Windows scenarios are still pending. T1059.001, T1059.003, T1027 and T1053.005 have no accepted recording yet; F-003 explains the rule and Atomic-test mismatches behind each. Pending scenarios count as zero in the 68%.
  • Small coverage. 14 techniques out of several hundred. The 68% is progress against this repo's own list, not a statement about any organization.
  • The cloud plane is replayed, not detonated by this project. The records are real CloudTrail from public datasets, but the cloud rules written for the project sit beside fixtures from the same datasets, so those passes show the wiring works, not that the rules generalize.
  • A different evaluator from production. There is no parity test against a real SIEM backend, so a pass is necessary, not sufficient.
