As foundA shell injection in its own Action, and the benchmark misses

Two things were wrong before 0.4.1, and both are in the repository's own changelog.

The first was in sinkline's own GitHub Action. Its inputs (path, fail-on, min-confidence) were interpolated straight into a shell line with ${{ inputs.* }}, so a workflow that passed an attacker-influenced value could run arbitrary commands on the runner. Version 0.4.1 passes them through env:, quoted, and tests/test_action.py runs the script with hostile values.

Script injection (CWE-78) happens when untrusted text is pasted into a shell command, so the shell runs it as code. Passing it as an environment variable keeps it as data.

The second was in the analysis. A try/except lost taint (a false negative): host = request.args["h"] followed by except: host = "localhost" reported nothing. The same release closed one of the benchmark's two remaining misses, a closure that reads tainted data, moving recall from 0.967 to 0.984 (changelog 0.4.1).

MethodHow it works

The problem

A pattern linter reports every cursor.execute whether the argument came from a config file or from request.args, so reviewers learn to ignore it. The useful question is whether attacker-controlled data can reach the sink without passing through something that neutralizes it for this bug class.

In web apps that answer usually crosses a function or file boundary: a view reads request.form and a helper two files away builds the SQL.

What it does

Pure Python on the standard ast module, with no dependencies. It knows Flask, FastAPI, Django and aiohttp sources, and has 42 rules with 138 sink signatures mapped to OWASP 2021 and CWE. Output is text, JSON, SARIF 2.1.0 (with code flows) or a self-contained HTML report. It also ships as a GitHub Action and a pre-commit hook, and supports --baseline so an existing codebase can fail only on new findings.

Three implementation points

Two-pass interprocedural summaries

Pass 1 analyzes each function with its parameters bound to symbolic labels (param:0, param:1, ...) and records which parameters reach the return value, which reach sinks, and whether the function is a thin sanitizer. It repeats until no summary changes, so a sink four helpers deep is found whatever order the helpers are defined in. Pass 2 re-runs with real sources and consults the summary at each call site. The cost is that summaries are context-insensitive: one per function, not per call site. Summary keys are module-qualified, so vulpy's bad/ and good/ trees, which define the same function names, give different results.

CWE-scoped sanitizers

A tainted value carries the set of CWEs it has been cleaned for. shlex.quote clears command injection only, html.escape clears XSS only, and int() clears everything. A single global "sanitized" flag makes a shell-safe string look SQL-safe. At a branch join, taint labels are unioned and cleared CWEs are intersected, so a value stays clean only if every path cleaned it. Validation guards such as if not x.isdigit(): abort() work the same way and are scoped too: a .. check is a path guard, not a shell guard.

CWE numbers name bug classes: CWE-78 is OS command injection, CWE-79 cross-site scripting, CWE-89 SQL injection.

try/except needs a real join

Version 0.4.1 fixed a false negative where host = request.args["h"] followed by except: host = "localhost" lost the taint, because the handler body was visited in sequence after the try body. Taint after a try is now the join of the body (plus else) and each handler that does not exit, with handlers entered from the join of every state the body passed through.

Tolerance and limitsWhat the numbers do not show

  • The benchmark is small and self-labeled. 109 lines, labeled by the same person who wrote the engine, and it doubles as the regression suite. Two of the 0.4.0 changes were written to fix lines in it. Read the scores as "no regressions and the design limits are visible", not as a generalization estimate.
  • The public-project scans are unlabeled. Three of the four are deliberately vulnerable training apps. Zero findings on microblog is consistent with its redirect check being treated as a guard, not proof the app is safe. No CVEs or real-world vulnerabilities are claimed.
  • Known design limits. Taint passed between requests through a module global (the one benchmark miss), returned closures, dynamic dispatch, and instance fields tracked per class rather than per object.
  • Python only, summaries context-insensitive, and no coverage for OWASP A04 and A06.
